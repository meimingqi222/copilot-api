## 1. 背景：为什么必须换

### 1.1 现状（v1）

`src/services/protocols/claude-native.ts` → `createClaudeMessagesOnce()`
→ 直接 `fetch https://api.anthropic.com/v1/messages?beta=true`，伪造全套 Claude Code 指纹：

| 伪造项                                     | 文件                                                 |
| ------------------------------------------ | ---------------------------------------------------- |
| `cch` 认证哈希（XXH64 + seed）             | `src/services/claude/cch.ts`                         |
| Cowork UA / 版本常量                       | `src/services/claude/fingerprint.ts`                 |
| Stainless 头 + beta 组合                   | `src/services/claude/headers.ts`                     |
| `x-anthropic-billing-hdr` + CC system 指令 | `src/services/claude/create-messages-once.ts`        |
| 工具名 `_` 前缀                            | `src/services/claude/tool-prefix.ts`                 |
| prompt caching / metadata user_id          | `src/services/claude/prompt-cache.ts` / `user-id.ts` |

### 1.2 为什么这套不安全

参考实现 magpie 在 `internal/gateway/claude_subscription.go` 文件头给出了准确判断：

> Anthropic applies subscription eligibility checks to request **content** (not just
> credentials/CCH); prompts generated by Pi, OpenCode and other harnesses can otherwise be
> routed to Extra Usage.

也就是说：**伪装的是"信封"，被检查的是"信的内容"。** 把 cch/UA/Stainless 做到完美也没用，
因为 `system[2+]` 里装的仍然是调用方（Copilot Chat / Pi / OpenCode / Codex）的 harness prompt，
而那正是内容分类器读的东西。

v1 还有两个结构性弱点：

- `fingerprint.ts` 里 `claudeCodeVersion = "2.1.220"` 是**硬编码**，靠人工跟版本；
  上游一发新版，UA 与 `cc_version` 派生出的 `cch` 就一起漂移。
- `cch` 的 seed / salt 是逆向常量，上游一改就全量失去认证，且无告警。

### 1.3 v2 的做法

**不再重放，驱动真正的 `claude` 二进制**：请求由真 Claude Code 生成并发出，
system prompt 由真 Claude Code 自己构造，内容分类器看到的就是货真价实的 Claude Code。

## 2. 硬约束（不得破坏）

1. **不要新增 `ProviderProtocol`。** 传输方式（HTTP 重放 vs CLI 子进程）是实现细节，
   不是上游 wire protocol。新增 protocol 会牵动 `PROVIDER_PROTOCOLS`、
   `protocol-provider.ts`、`MODEL_ENDPOINTS`、admin UI、provider presets、quota fetchers
   等一大片，收益为零。**用 connection 级开关，见 §4.1。**

2. **不要动 `provider-connections.json` 的 schema。** 开关存 `connection.metadata`，
   不新增 typed 字段、不 bump schema version、不改 admin API 响应形状
   （admin 响应形状是冻结的，见 `AGENTS.md` 的 G1 约定）。

3. **refresh token 的唯一持有者必须是 copilot-api。**
   CLI 只通过环境变量 `CLAUDE_CODE_OAUTH_TOKEN` 拿到 access token，**绝不允许 CLI 自己刷新**。
   现有刷新链路（`src/services/oauth/refresh-strategies.ts` 的 `claude` 分支，
   lead 4h）保持不变。这是 magpie 用 `logins.json` + `savedTokenMu` 费力维持的不变量，
   在我们这里由"每个 connection 独立凭证"天然满足。

4. **不要动 v1 的任何代码路径。** 只允许在 `createClaudeMessagesOnce()` 顶部加一个分支。

5. **不要动 dispatch / failover / usage-recorder 的接口。**
   adapter 契约（`ProtocolAdapter.createMessages`）保持不变：
   返回 `AsyncIterable<unknown>`（Anthropic SSE 事件）或 `Record<string, unknown>`（非流式响应）。

## 4. 架构

### 4.1 传输选择

```
connection.metadata.claudeTransport  ∈  {"cli", "http"}    // 缺省 = auto
环境变量 COPILOT_API_CLAUDE_TRANSPORT = "http"             // 全局 kill-switch，优先级最高
```

`resolveClaudeTransport(connection)`：

1. `COPILOT_API_CLAUDE_TRANSPORT === "http"` → `"http"`
2. `connection.metadata.claudeTransport === "http"` → `"http"`
3. `connection.metadata.claudeTransport === "cli"` → `"cli"`（找不到二进制时抛错，**不**静默回落）
4. 否则 auto：`findClaudeBinary() !== undefined` → `"cli"`，否则 `"http"`

> 显式指定 `"cli"` 时找不到二进制要**报错**而不是回落 —— 静默回落会让人以为在用安全路径，
> 实际在跑 v1，这是最危险的失败模式。

### 4.2 数据流

```
POST /v1/messages
  └─ dispatchMessages → executeWithFailover → claudeNativeAdapter.createMessages
       └─ createClaudeMessagesOnce
            └─ [transport === "cli"]  bridge.serve()
                 ├─ findParkedRun(payload)      ← 命中？唤醒
                 │    └─ run.resume(toolResults) → 新 SSE segment
                 └─ 未命中？runRegistry.start()
                      ├─ mkdtemp → tools.json / mcp.json
                      ├─ Bun.spawn(claude, args, env)
                      ├─ 写一条 user 消息到 stdin，关 stdin
                      └─ 读 stdout 的 stream-json → Anthropic SSE

  CLI 侧 tools/call
    └─ claude → stdio MCP helper（子进程）
         └─ POST http://127.0.0.1:<port>/_internal/claude-mcp/<token>
              └─ 阻塞，直到调用方带回 tool_result
```

### 4.3 关键机制：tool_use id 的传递

**这是整个方案能不能成立的支点，必须理解清楚：**

- CLI 在 `tools/call` 的 `params._meta["claudecode/toolUseId"]` 里带上它要调用的
  `tool_use` 块的 id（见 `internal/claudebridge/mcp.go:110`）。
- 网关把这个 id 当作**关联键**：它同时也出现在网关返回给调用方的
  `content_block_start`（`type: "tool_use"`, `id: toolu_...`）里。
- 调用方下一轮请求带回 `tool_result { tool_use_id: "toolu_..." }`，
  网关据此在 registry 里找到那个**正阻塞在 MCP `tools/call` 上的** run，把结果投递进去，
  CLI 就继续跑同一轮。

没有 `_meta["claudecode/toolUseId"]` 这条通路，就只能靠顺序猜，必然错。

### 4.4 进程生命周期

- **一回合 = 一个进程**。写完第一条 user 消息后 `stdin.Close()`，CLI 跑完这轮就退出。
- 跨回合**不复用**进程（magpie 也不复用）。
- 一轮之内跨多次工具调用**复用**同一进程 —— 这是 prompt cache 命中率的关键，
  也是"挂起而不是重开"的根本理由。
- 30 分钟兜底：`setTimeout(30 * 60_000, () => run.abort())`，每轮 `resume` 时重置。

  - `POST /_internal/claude-mcp/:token`，body `{tool_call_id, name, arguments}`。
  - 从 `runRegistry` 按 token 找 run；找不到 → 404。
  - 把 `tool_call_id` 注册进 `run.pending`，然后**阻塞等待**调用方带回结果。
  - 超时（`patience`，建议 60s）：把 waiter 挪进 `run.late`，立刻返回
    "这个调用还在跑，请调 `magpie_wait`（我们叫 `wait_for_tool`）等结果，不要重复调用"。
  - 这个端点是**内部**端点：绑定在 loopback，且 token 是一次性随机值。
- `src/services/claude/cli/run-registry.ts`
  - `Map<token, Run>` 与 `Map<toolUseId, Run>`
  - `findParkedRun(payload)` —— 收集 payload 里所有 `tool_result` 的 `tool_use_id`，
    查表；**必须全部指向同一个 run**，否则视为不匹配（照 `findRun()`）。
  - `continueWith(run, results)` —— 逐个投递给 `pending` waiter，并挂新的 SSE segment。
- `src/services/claude/cli/bridge.ts`
  - `serve({ connection, credential, payload, signal })` 编排：
    1. `findParkedRun` 命中 → `continueWith`，返回新 segment；
    2. 未命中 → 建临时目录、写 `tools.json` / `mcp.json`、spawn、
       写第一条 user 消息、`stdin.Close()`、返回初始 segment。
  - **首事件 peek**（照 `serveSubscription()`，`claude_subscription.go:676`）：
    返回之前先把头部事件读出来，如果第一个非 `message_start` / `message_delta` 的事件是错误，
    **不要返回流**，而是抛 `HTTPError(429|502)` ——
    这样 `executeWithFailover` 才能换下一个账号。
    配额类文案（`quotaWords` 正则，见 `internal/gateway/fallback.go:191`）映射成 429。
- `src/main.ts` —— 加隐藏子命令
  ```ts
  subCommands: { auth, start, debug, key, "claude-mcp-helper": claudeMcpHelper }
  ```
  （不要写进 README 的用户可见命令列表）

**MCP 配置 JSON**（写进临时文件，用 `--mcp-config` 传路径）

```jsonc

    "copilotapi": {
      "command": "<process.execPath>",
      "args": ["claude-mcp-helper", "<callbackUrl>", "<toolsJsonPath>"],
    },
```

**工具名与前缀**

- 调用方工具名 → MCP 工具名：加前缀（例如 `mcp__copilotapi__` 由 CLI 自己拼，
  我们只需保证 `tools/list` 里给出原名）。

  v1 的 `tool-prefix.ts` 是 `_` 前缀方案，**CLI 路径不要复用它**，写一个独立的剥离函数。

**超时/唤醒语义**

MCP 客户端大约 1 分钟就放弃一次 `tools/call`。所以：

- `patience`（默认 60s）到点后返回"还在跑，调 `wait_for_tool`"，
  并把 waiter 放进 `run.late`；
- 调用方（或模型）改调 `wait_for_tool`，我们再阻塞最多 `patience`；
- 调用方带回真实 `tool_result` 时，投递给 `late` 里的 waiter。

> 简化选项：如果调用方是单轮"先拿 tool_use 再回 tool_result"的模型（Pi/OpenCode 都是），
> 那 `patience` 可以设得很大（如 5 分钟）并**先不实现 `wait_for_tool`**，
> 在 Phase 3 的验收里记为已知限制。请先按简单版本实现，把 `wait_for_tool`

## 6. 已知坑

### 6.1 跨回合 prompt cache 的前缀稳定性

Anthropic 的 prompt cache 是**前缀缓存**：token 流从第一个 token 开始比对。

- `renderClaudePrompt` 必须是**纯顺序拼接、无头无尾**，
  这样 `render(msgs[0..N])` 才是 `render(msgs[0..N+1])` 的字符串前缀。
  **不要**在渲染里加入消息总数、时间戳、随机 id 之类的东西。
- **cwd 会进 system prompt。** 若每回合换一个随机临时目录，
  system prompt 的第一个 token 就变了 → 全量 miss。
  → 必须用持久化的 `claudeHome`（Phase 1 / Phase 5）。
- **工具集变了会全废。** 工具定义在 token 流里位于 messages 之前，
  所以调用方增删工具（MCP server 连/断、动态工具）会让整段对话 miss。
  → 在 `tools/list` 输出里对工具做**稳定排序**（按 name），减少无谓抖动。

### 6.2 工具名前缀必须双向一致

CLI 返回的 `tool_use.name` 带 MCP 前缀（`mcp__<server>__<tool>`），
必须剥掉再给调用方；调用方下一轮带回来的 `tool_result` 只有 `tool_use_id`，没有名字，
所以关联只能靠 id。**不要**尝试用名字关联。

### 6.3 `_meta["claudecode/toolUseId"]` 取不到时

Grok/Cursor 那类 agent 不传这个字段（magpie 就是为此才自己生成 id）。
Claude Code 会传。但我们仍要实现兜底：
取不到就自己生成 `call_<random>`，并且**必须确保这条路径下 `tool_result` 也能关联上** ——
做不到就把该次调用直接判为错误，宁可失败也不要错配。

### 6.4 首事件 peek 是 failover 的前提

`executeWithFailover` 只能在没有向下游写出任何字节时切换账号。
所以 adapter **必须**在返回流之前把头部事件读完并判定成败，
否则配额/限流错误会以 `200 + event: error` 的形式发给客户端，failover 永远不触发。

参考 `serveSubscription()` 的做法，以及 `src/routes/messages/connection-handler.ts`
里已有的 "Phase 1: dispatch BEFORE the downstream SSE response exists" 约定。

### 6.5 多租户下的 registry 隔离

magpie 是单用户本机工具，`tool_use.id` 全局匹配没问题。
copilot-api 是多租户代理，**必须**把挂起的 run 绑定到 admission 的 owner/connection，
唤醒时校验来源身份，否则 A 用户可以用 B 的 `tool_use_id` 劫持 B 的挂起进程。
→ `findParkedRun` 要带上 `connectionId` / `credentialId` 做校验，不匹配就当未命中。

### 6.6 不要把 CLI 路径接到 `prompt-cache.ts` / `cch.ts` / `headers.ts`

这三个模块是 v1 独有的。CLI 路径下它们全部不参与。
唯一还要用的是 `fingerprint.ts` 的版本号 —— 而那个也应该改成读
`claudeVersion()`（Phase 1），不要再硬编码。

### 6.7 Bun 的 spawn 细节

- 用 `Bun.spawn`，`stdin: "pipe"` / `stdout: "pipe"` / `stderr: "pipe"`。
- `env` 必须传**完整替换后的对象**（Bun 的 `env` 是覆盖式，不是增量）。
- stdout 是**换行分隔的 JSON**，用 `for await (const chunk of proc.stdout)` +
  行缓冲，注意跨 chunk 的半行。
- `proc.exited` 是 Promise，用它做 `finish()`。
